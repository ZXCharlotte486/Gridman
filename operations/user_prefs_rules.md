# 用户偏好与协作画像规则

> 何时读本文件：阶段①需要加载用户上下文时，或用户表达、修改、撤销稳定偏好时。
> 本文件管理“属于用户本人、跨项目稳定复用”的协作偏好与约束；不限于输出格式、浏览器或工具。


## 一、职责定义

`gridman-mind/01_projects/user_prefs.md` 是用户的跨项目协作画像，用于让古立特在不同任务中持续采用用户认可的沟通、判断、执行和交付方式。

一条信息只有同时满足以下条件，才适合写入：

1. **主体是用户本人**：描述用户希望如何协作，而不是某个企业或项目的事实；
2. **具有稳定性**：预计后续仍会适用，而非仅限本轮；
3. **具有复用性**：可影响多个项目或多类任务；
4. **用户可控制**：用户能够随时修改、撤销或覆盖；
5. **允许持久化**：不属于凭证、密钥或不应长期保存的敏感信息。

不确定是否长期有效时，先作为本轮要求执行，不擅自写入偏好。


## 二、可以记录的偏好类型

| 类型 | 典型内容 |
|---|---|
| 沟通与称呼 | 称呼方式、语言、术语密度、解释深度、是否先给结论 |
| 输出与呈现 | 文件格式、模板、表格风格、引用方式、命名习惯、篇幅 |
| 工作方式 | 先讨论还是直接执行、是否分阶段汇报、是否展示过程、工作节奏 |
| 决策方式 | 希望提供几个方案、是否给推荐结论、偏好的权衡维度、何时必须询问 |
| 风险与审慎度 | 风险容忍度、保守或激进口径、重大判断所需证据、复核强度 |
| 授权与确认 | 哪类低风险动作可直接执行、哪类动作必须逐步确认；不得降低系统强制安全边界 |
| 隐私与数据 | 默认脱敏要求、允许使用的外部服务、禁止外传的数据类型、留存偏好 |
| 工具与环境 | 浏览器偏好、可见窗口、优先使用的工具、操作系统或路径习惯 |
| 文件与归档 | 默认工作目录、命名规范、版本保留、根目录整洁等用户附加要求 |
| 专业口径 | 用户长期采用的会计政策偏好、审计表达习惯、税务判断呈现方式；具体企业事实仍归企业/项目卡 |
| 时间与提醒 | 时区、日期格式、截止日表达、提醒频率、是否主动提示待办 |
| 协作禁区 | 不自动发邮件、不代为提交、不做未经确认的外部写入等稳定限制 |
| 无障碍与可用性 | 字号、颜色、键盘优先、避免特定格式、阅读辅助需求 |
| 其他稳定偏好 | 任何满足本文件五项判断标准、且不属于排除项的跨项目协作要求 |

该表是分类参考，不是封闭清单。新类型满足职责定义即可记录，不必为了归类而遗漏。


## 三、不得记录为用户偏好的内容

| 内容 | 正确去向或处理方式 |
|---|---|
| 某企业资料、会计政策事实、项目口径、截止日和进度 | `01_projects/{企业名}.md` 或 `{项目名}.md` |
| 用户原始文件与业务数据 | `02_input/`，按项目管理 |
| 临时中间结果 | `03_temp/`，任务结束按规则清理 |
| 正式交付物 | `04_outputs/` |
| 真实错误、判断理由和改进提案 | `05_learning/` 对应文件 |
| Gridman 对所有用户都应遵守的通用制度 | Skill 的 operations、Workflow 或知识规则 |
| API key、token、密码、私钥、Cookie 等凭证 | 不进入 Mind；按 Tools 凭证规则隔离 |
| 仅本轮有效的命令或临时要求 | 本轮上下文执行，不持久化 |
| 助手自行推测的性格、身份、敏感属性或偏好 | 不记录；需要时向用户确认 |

用户偏好可以在通用规则之上增加更严格的个人约束，但不能覆盖系统安全要求、专业底线或强制授权规则。


## 四、识别与确认规则

### 直接记录

用户明确表达长期性时，可在同轮末尾记录，例如：

- “以后都……”
- “默认……”
- “我习惯……”
- “每次都……”
- “不要再……”
- “记住我的偏好……”

### 先确认再记录

出现以下情况时先询问是否设为长期偏好：

- 用户只说了本次要求，但可能具有长期价值；
- 同一要求在多个任务中重复出现，但用户没有明确长期化；
- 新偏好与已有偏好冲突；
- 偏好的适用范围不清楚，例如仅限审计项目还是所有任务。

### 不得自动推断

不能仅根据一次选择、浏览行为、文件内容或助手猜测建立长期画像。反复纠正可以作为询问依据，但不能替代用户确认。


## 五、读取与应用规则

- 需要 Mind 上下文的会话，在阶段①优先读取 `01_projects/user_prefs.md`。
- 只应用与当前任务相关的偏好，不机械复述全部画像。
- 执行前检查偏好是否与当前明确指令冲突；当前明确指令优先，但不自动改写长期偏好。
- 交付前检查沟通、格式、路径、风险和隐私要求是否满足。
- 偏好与系统安全、法律合规、专业底线冲突时，不执行冲突部分，并简要说明原因。
- 偏好过期、条件变化或无法适用时，主动确认，不盲目沿用。


## 六、写入、更新与撤销

- 用户明确新增、修改或撤销偏好时，在同轮末尾更新。
- 按主题维护当前有效偏好，并在文末追加更新记录；不要只堆叠相互矛盾的历史句子。
- 修改时保留必要的变更轨迹，但正文只呈现当前有效状态。
- 用户说“这次例外”时只影响本轮，不改长期偏好。
- 用户说“以后改为……”时更新当前规则，并记录变更日期。
- 用户要求忘记某项偏好时，删除当前有效项并记录撤销，不继续据此行动。
- 不存在 `user_prefs.md` 且用户尚未表达稳定偏好时，不为形式完整而创建虚假内容。


## 七、推荐文件结构

```markdown
# 用户偏好（User Preferences）

> 最后更新：YYYY-MM-DD
> 本文件仅保存用户本人稳定、跨项目的协作偏好。

## 沟通与决策
- 先给结论，再说明依据。
- 重大选择提供备选方案和推荐意见。

## 风险、授权与隐私
- 外部上传前确认数据范围和脱敏要求。
- 不自动发送邮件或提交外部系统。

## 输出与文件
- 报告优先使用 Markdown。
- 不在项目根目录遗留临时文件。

## 工具与环境
- Playwright 使用可见浏览器窗口。

---
## 更新记录
- YYYY-MM-DD：新增……
- YYYY-MM-DD：将……修改为……
- YYYY-MM-DD：撤销……
```

结构可按实际偏好扩展，不要求保留空章节。


## 八、与其他规则的边界

- `operations/private_resources_rules.md`：管理 Mind/Tools 的定位、目录职责、文件落位与安全边界；这是通用制度。
- `operations/user_prefs_rules.md`：管理当前用户稳定、跨项目的协作画像；这是个性化要求。
- 企业卡和项目卡：管理具体业务事实、项目口径与进度。
- `operations/behavior_rules.md`：管理不可被用户偏好覆盖的常驻行为与专业底线。

同一内容不得在通用规则和用户偏好中重复维护。若某项要求后来被提升为 Gridman 的通用制度，应从用户偏好中精简为用户附加要求或删除重复表述。
